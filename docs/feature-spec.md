# 功能 Spec 规范

## 一项功能，一份主 Spec

每项用户可见功能必须对应一份独立的主规格（Spec），由[功能索引](README.md#功能规格spec)指向。Spec 说明已经确认的行为、边界与验收条件，是实现和测试的共同依据；设计草稿、研究记录和更新日志不能代替它。

主 Spec 位于 `src/features/<id>/spec.md`，与功能实现、文案和测试共同维护，并随模块代码提供。原 `docs/` 功能正文已迁移，不保留重复权威版本；目录或链接变化同步索引与分发清单，遵循[特性模块约定](feature-modules.md)。已有 Spec 不等于所有验收条件已经通过，既有规格按功能变更继续补齐下述内容。

一项功能可包含若干内部能力和配置。例如通知声音归任务通知 Spec，MCP 提供方解析归 MCP 管理 Spec。基础队列、共享控件和通用 codec 不因为独立成文件就成为用户功能。不同主开关控制的独立用户功能各有 Spec；共用菜单或底层机制不将它们合并。

## 必须说明的内容

| 内容 | 要回答的问题 |
| --- | --- |
| 标识、入口与状态 | 功能叫什么、稳定 id 是什么、从哪里进入？哪些行为已实现，哪些仍为提案？ |
| 目标与范围 | 解决什么问题？保留什么？明确不包含哪些相邻能力？ |
| 配置与兼容 | 配置键、默认值、保存位置、读写权限及既有数据如何保留？ |
| 行为 | 开启、关闭、用户操作、失败、重试、并发和过期响应分别如何处理？ |
| 生命周期 | 停用入口、停用模块、卸载及宿主重载时，哪些状态保留、哪些副作用释放？ |
| 宿主与平台 | 使用哪些已核对的公共能力？服务缺席、平台不支持及版本差异如何表现？ |
| 数据与权限 | 读取或写入哪些数据、配置或文件？是否有网络、进程、凭据或 DOM 接入？ |
| 验收条件与证据 | 可观察的成功、失败和清理条件是什么？对应哪些测试，实际验收还有哪些未执行？ |

简单功能可以使用简短段落覆盖这些信息，不强制为了格式写八个章节。无需 RPC、网络、文件或持久数据时明确说明不涉及，不创建空接口或占位实现。宿主 API 必须有来源，不把项目内部接口草图写成已存在的宿主能力。

验收条件用可观察的输入和结果表达，例如：「保存失败后开关回到已保存状态，监听数量不增加」。不能只写「功能正常」「符合设计」或用源码函数存在证明操作有效。

## 开发与变更规则

1. 新增功能先建立最小 Spec，明确用户已确认的范围，再实现。未确定的内容标为提案，不因写入文档而获得实现授权。
2. 修改用户行为、默认值、数据、协议或权限时，同步对应 Spec 与必要测试；纯内部重构可只更新实现定位与验证说明。
3. 既有配置键和对外 RPC 不随目录或功能 id 改名。确需变化时，Spec 必须说明兼容策略及用户需要的操作。
4. 测试与实际验收分开记录；静态检查、安装成功、Client 注册及实际页面分别陈述，不能相互替代。
5. 装配清单通过纯定义关联模块 id、配置键与唯一 Spec；仓库检查核对两端登记、未登记目录、Spec 索引、功能测试与依赖边界，实际包检查核对 Spec 随代码提供。新增功能时同步这些登记，不能只创建文档或空目录。

## 最小模板

```markdown
# 功能名称

## 标识、入口与范围

功能 id、用户入口、已确认目标、保留范围与不包含的能力。

## 配置与行为

配置键与默认值；保存方式；开启、关闭、具体操作、失败与并发行为。

## 生命周期、权限与兼容

关闭入口和卸载的差异；资源释放；数据读写与权限；宿主接口依据、平台限制与不可用行为。

## 验收条件与验证

可观察的成功、失败和清理条件；对应实现与测试链接；已执行的验证及仍未验证的项目。
```
